2. 构建（两步编译链）

本仓库的包没有独立的 build 脚本（package.json 里 scripts 为空，根目录的 pnpm build 是全仓 + 前端的大流程，不需要）。构建必须手动走两步：先 tsc 后 tsdown，顺序不能反——tsdown 的 entry 指向 tsc 的产物。

Step 1 — tsc 编译（产出 lib/types/*.js）

cd /home/z00573109/deepseek-harness
npx tsc -b packages/llm/llm-agent-hint --force

# 验证产物：
ls packages/llm/llm-agent-hint/lib/types/index.js     # 应存在

--force 全量重编（增量状态陈旧时稳妥）。依赖包（cordis/llm 等）若有问题 tsc 会顺带报错。

Step 2 — tsdown 打包（产出 lib/index.js）

cd /home/z00573109/deepseek-harness
npx tsdown --env.DSH_BUILD_FACE host

# 验证产物：
ls packages/llm/llm-agent-hint/lib/index.js   # 应存在（插件入口，exports "." 的落点）
为什么 tsdown 报 "Cannot find entry"： tsdown 一次构建整个 workspace（host 面 workspace: ['vendor/*', 'packages/*/*', 'apps/cli', 'apps/desktop-host']，entry 为 lib/types/{index,invariant,startup}.js）。如果 agent-hint 还没跑过 tsc（lib/types 为空），它会在解析阶段就失败——报错会指名 [@deepseek-ai/dsh-llm-agent-hint] Cannot find entry。解法就是回到 Step 1 先把包 tsc 编译掉。

4. 运行

4.1 启动抓包代理（先于 web）

新架构要同时观察两个端口语义：数据面走 Anthropic Messages（适配器向 baseURL 追加 /v1/messages，日志标 DATA），控制面仍是空 messages 的 OpenAI chat-completions（默认派生 <baseURL>/v1/chat/completions，可被 agentHint.sessionControl.endpoint 覆盖，日志标 CONTROL）。代理同时接收这两条路径，打印 agent_hint 后原样转发真实 coordinator（UPSTREAM，默认 1025）。 
# 已在跑则跳过（pgrep 有输出即在跑）——但必须先确认它绑在 1026，而不是 3080
pgrep -af agent-hint-watch.mjs
ss -ltnp 2>/dev/null | grep -E ':1026|:3080'   # 3080 必须空着：那一个留给 dsh web
nohup node /home/z00573109/deepseek-harness/agent-hint-watch.mjs > /tmp/agent-hint-watch.log 2>&1 &

# 启动后回读端口（应打印 http://127.0.0.1:1026 -> http://127.0.0.1:1025）
tail -1 /tmp/agent-hint-watch.log

# 健康检查（透传到 coordinator）：
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:1025/v1/models   # 期望 200

可选环境变量：PORT（默认 1026）、VERBOSE=1（打印完整请求体）、UPSTREAM（默认 http://127.0.0.1:1025）。

代理绝不能占 3080（2026-10-14 事故）：脚本早先的 PORT 默认值是 3080，与 dsh web 的监听端口重合。此时 dsh web 启动报 EADDRINUSE 127.0.0.1:3080，并连带刷出 9 个插件"等待服务"（webRuntime/connection/web-runtime 等）——那全是 webserver 起不来后的级联，不是各自独立故障。而 agent 路由指向 1026，这个代理等同于白跑。默认值已改为 1026；若日志仍显示绑在 3080，说明是旧启动或显式设了 PORT=3080。
代理已加固（2026-10-08）：协调器 PD 分离调度可能 stall 数分钟，undici 默认 300s body/header 超时会杀死中继并连带崩溃进程。脚本已内置 headersTimeout: 0, bodyTimeout: 0 与流 error 兜底（error 只终结该响应，不终结进程）。修改脚本后需重启代理生效。

4.3 配置自检（新环境/排障时必做）

v0.2.0 的 composition 全是 patch 层：home 级 ~/.dsh/cordis.patch.yml（对所有 profile 生效，优先级最高）与 profile 级 ~/.dsh/profiles/web/cordis.patch.yml。UI 的模型选择也会写进 profile 层——保存过的 UI 选择（Volatile 语义）覆盖 cordis 默认值，这是"发消息没流量"的头号原因。

v0.2.0 patch 的 id 定向语法不能新增条目（本次事故根因）：- id: llm-agent-hint ... 只覆盖已存在的条目；目标不存在时 loader 仅告警 patch: entry "llm-agent-hint" not found 并跳过——插件从未加载，全部请求无 agent_hint。新增插件条目必须用 - insert: 语法（无 id 时 push 到根列表）。

实测生效的最小挂载（profile 层 ~/.dsh/profiles/web/cordis.patch.yml）：

- insert:
    - id: llm-agent-hint
      name: '@deepseek-ai/dsh-llm-agent-hint'
      config:
        baseURL: http://127.0.0.1:1026   # 数据面 POST <baseURL>/v1/messages；控制面派生 <baseURL>/v1/chat/completions
        models:
          - id: DeepSeek-V4-Flash-0731-w8a8   # 本环境模型 id
        # apiKeyEnv 省略即可：路由不发 authorization 头，无需任何 key
        # 如需带 key，写 apiKeyEnv: MOTOR_API_KEY 并通过 Models 页/环境变量提供，缺失则报 MISSING_CREDENTIAL
- id: agent-default-model
  name: "@deepseek-ai/dsh-agent-default-model"
  config:
    provider: deepseek-agent-hint     # 固定默认路由；UI 选择会覆盖它
    model: DeepSeek-V4-Flash-0731-w8a8

patch 文件热重载，改完不用重启；但会话创建时钉住路由——旧会话永不改走新路由，改完必须新建会话验证。快速验证组合树（不启动服务）：

cd /home/z00573109/deepseek-harness
pnpm dsh web --dump-config 2>&1 | grep -B2 -A10 llm-agent-hint
# 能看到 llm-agent-hint 条目 + provider: deepseek-agent-hint，且无 "not found" 告警即正确

5. 验证

5.1 浏览器操作

  1. 先在 PC 电脑执行 ssh 隧道，把 PC 的 3080 端口直连到服务器 192.168.13.173：
    ssh -f -N -g -L 3080:127.0.0.1:3080 root@192.168.13.173 -o ServerAliveInterval=30
  2. 打开 http://127.0.0.1:3080/?token=<启动日志中的 token>
  3. 新建会话（旧会话在创建时已锁定旧 provider，改设置只对新会话生效）
  4. 发第一条消息
  5. 同一会话再发第二条（观察纯身份形态）
  6. 输入 /compact 触发压缩（见 5.3 的成功条件）

5.2 看日志

tail -f /tmp/agent-hint-watch.log

数据面（标 DATA，走 /v1/messages）：

[hh:mm:ss] DATA    POST /v1/messages stream=true messages=1
  agent_hint: {"session_id":"session-...","session_control":{"type":"start"}}  # 首条普通请求
[hh:mm:ss] DATA    POST /v1/messages stream=true messages=3
  agent_hint: {"session_id":"session-..."}                                     # 第二条起：纯身份

控制面（标 CONTROL，走 /v1/chat/completions，空 messages）：

[hh:mm:ss] CONTROL POST /v1/chat/completions stream=false messages=0
  agent_hint: {"session_id":"session-...","session_control":{"type":"stop"}}

六种动词的触发时机与实测形态（2026-10-08 全部抓包确认）：

动词触发时机实测备注
startfresh 会话首条被接受的普通请求（2xx 头到达即记账）已验证 挂在首条消息而非建会话
纯身份 {session_id}start 记账后的所有普通请求已验证 压缩后的请求也保持纯身份，不重发 start
pause另一会话产生被接受的普通请求时，原前台会话到达 idle已验证 纯 UI 切换无流量、不发 pause（设计内）
resume已有内容的会话输入草稿（session/composing，空→非空跃迁单次触发）已验证
stop会话归档（workspace/session-archived，advisory）或销毁（session/disposed，terminal）已验证 健康时单发
compactcompaction/end 无 error（压缩成功），请协调器 evict-and-rebuild已验证 成功单发；失败不发（见 5.3）

标题生成、压缩摘要等后台调用（purpose 已定义）不携带 agent_hint（日志 agent_hint: <absent>），是设计内行为（匿名调用不扰动 KV-cache 身份）。

失败窗口的"双发"不是缺陷：控制面客户端 retries=1，非 2xx 或网络错误时有界重试一次。协调器 503（PDRole.ROLE_U: No instance available）期间，stop/resume 会在日志出现恰好 2 条（attempt+retry）；协调器健康时同一操作只有 1 条。管理请求（空 messages）不受推理容量影响，503 期仍 200。

5.3 compact 专项：成功条件与失败语义

  • 体量护栏：摘要必须比被替换内容短，否则压缩失败并记入会话日志：summary is not smaller than the shadowed content (摘要 tokens >= 被影 tokens)。只影非最近回合——1~2 个短问答的会话几乎必然触发护栏。
  • 可复现的成功路径：先发 2~3 个长回答消息（如"推荐三个旅游攻略，每个 300 字"），让早期长回答进入可压缩区，再 /compact。实测 3 回合后成功：「已压缩 6 条历史记录（约 663 tokens）」。
  • 失败不发动词：compaction/end 带 error 时 bridge 直接返回，控制面零请求；成功才发单次 compact。两种情形都已抓包确认。
  • 压缩摘要请求本身（DATA，purpose 已定义）不带 agent_hint；压缩成功后下一条普通请求仍是纯身份（compact 动词已让协调器完成 evict-and-rebuild）。

7. 故障排查

症状原因与解法
pnpm: command not found 环境无 pnpm 且无 corepack。npm i -g pnpm@11.7.0（对齐 packageManager 字段）后 pnpm install
web 启动卡死、长时间无输出 inotify 限额被系统重置（默认 watches=8192/instances=128，chokidar 监听整个仓库直接耗尽）。重设：sysctl -w fs.inotify.max_user_watches=524288 fs.inotify.max_user_instances=512（重启后需重设）
启动报 listen EADDRINUSE 127.0.0.1:3080 先查清占用者是谁，不要默认是 web 残留：ss -ltnp | grep :3080。
① 占用者是 dsh web（上次启动未停）→ pkill -INT -f "dsh web" 优雅退出后重启；-9 会跳过 teardown，stop 控制请求发不出。
② 占用者是 agent-hint-watch.mjs（2026-10-14 实例：PORT 未设而旧默认值为 3080）→ pkill -f agent-hint-watch.mjs，再按 4.1 在 1026 重启；此时 web 从未启动过，且代理也没接到任何 agent 流量。
两种情形都会连带刷出多个插件"等待服务"，那是 webserver 失败的级联。反向同理：1026 被占会让代理 EADDRINUSE 崩溃，pgrep -af agent-hint-watch 排查
dump-config 报 patch: entry "llm-agent-hint" not found 本次事故根因：patch 用 id 定向语法新增条目，v0.2.0 loader 只覆盖已存在条目，未命中即告警跳过，插件从未加载。改用 - insert: 语法（见 4.3），并把 agent-default-model 切到 deepseek-agent-hint，重启后新建会话验证
tsdown 报 Cannot find entry: ["lib/types/{index,invariant,startup}.js"] workspace 里某个包（报错会指名）还没跑 tsc，lib/types 为空。对指名的包先 npx tsc -b <包路径> --force 再重来 tsdown；tsc 增量状态陈旧时同样用 --force 全量重编
web 启动报 ERR_PACKAGE_PATH_NOT_EXPORTED / 模块找不到 dsh-llm-agent-hint lib/index.js 没构建（回第 2 节）；或 profile 里的 link 安装指向了旧路径，重跑第 3 节的 dsh plugin add
web 正常回复但代理零流量 / 有流量无 agent_hint 请求没走 agent-hint 路由。UI 的模型选择保存在 profile patch 层并覆盖 cordis 默认值——查 ~/.dsh/profiles/web/cordis.patch.yml 里 agent-default-model 的 provider 是否 deepseek-agent-hint，改完新建会话再发（旧会话创建时钉住旧路由）。若收到 /v1/messages 但无 agent_hint 字段，说明 prepareExtensions 没挂上或插件未组合进 profile（见上一条）
日志里 stop / resume 同秒出现 2 条 协调器 503 或网络错误窗口的有界重试（retries=1，attempt+retry=2），设计的容错行为。协调器健康时同一操作恰好 1 条——可用健康期再操作一次对照验证
UI 报"处理失败 TRANSPORT"、推理 503 PDRole.ROLE_U: No instance available 协调器 PD 分离调度容量劣化，推理后端无可用实例——环境问题，找推理后端负责人。管理请求（空 messages）不受影响仍 200，控制面动词照常
/compact 报 "Compaction could not produce a useful summary" 体量护栏：摘要不短于被替换内容（会话日志有具体 token 数）。会话太短/内容太新时属正常。先发 2~3 个长回答消息再压缩；失败不会产生 compact 控制请求（设计内）
切换会话时没有任何带 agent_hint 的请求 纯 UI 切换不产生 LLM 流量，pause 只在另一会话产生被接受的普通请求时触发——设计内行为，与 v0.1.1 一致。想观察 pause：在 A 会话发消息后，切到 B 会话发消息，A 会收到 pause
浏览器打不开 3080 / ERR_CONNECTION_REFUSED 跨机器访问靠 VS Code 端口转发，确认转发的是 3080 且 URL 带 ?token=...（token 在 web 启动日志里）；未转发的端口（如 3081）不可达
vitest 报 "No test files found" 在包目录里跑的。回到仓库根目录：pnpm exec vitest run packages/llm/llm-agent-hint
配了 apiKeyEnv 却报 MISSING_CREDENTIAL 显式写了 apiKeyEnv: MOTOR_API_KEY 但该引用解析为空。补一个非空值（Models 页保存，或启动环境导出，或写进仓库根 .env）；不想要 key 就直接删掉这一行——省略 apiKeyEnv 时路由不发 authorization 头，天然免 key
